# Alif (alifpay) API: transport, auth, errors, webhooks, sandbox

Hand-written notes. Applies to every Alif product in this skill.

- Source: https://docs.alifpay.uz/ (introduction) and https://docs.alifpay.uz/changelog/ (Russian pages)
- Fetched: 2026-11-03
- Doc version covered: the "current" API (`/pay`, `/invoice` with `payment`). The original
  version (`/purchase`, `ref`, `charge`) is still served but frozen; do not build on it.

## Transport

| Item | Value |
|---|---|
| Base URL (production) | `https://api.alifpay.uz/v2` |
| Base URL (sandbox) | `https://api-dev.alifpay.uz/v2` (hosted page: `https://checkout-dev.alifpay.uz`) |
| Style | HTTP RPC: method name in the path (`POST /v2/pay`), JSON body, always `POST` |
| Auth | header `Token: <API_TOKEN>`; separate tokens for sandbox and production |
| Branch auth (beta) | header `Store-Token: <STORE_TOKEN>` instead of `Token` |
| Content type | `Content-Type: application/json` |
| Amounts | integer **tiyin** (1 UZS = 100) |
| Times | ISO-8601 strings (`2026-11-03T08:00:00Z`) |
| Phones | `998NNNNNNNNN` (12 digits, no `+`) in requests; masked strings in responses |

## Response and error envelope

- Success: HTTP 200 with the method's result object (no wrapper).
- Business, validation and internal errors: **also HTTP 200**, body
  `{"error": {"code": <int>, "message": "<text>"}}`. Always check for `error` before reading
  the result.
- Auth failures and network-level failures: non-200 HTTP status.
- `message` is human-readable and case-specific; branch on `code`.

| Code | Meaning | Retry? |
|---|---|---|
| 1001 | bad request body (invalid JSON, wrong attribute type) | no |
| 1002 | unauthorized (wrong token) | no |
| 1003 | internal / unknown error | yes |
| 1004 | not found (card, payment, ...) | yes |
| 1005 | invalid params (amount, empty field, ...) | no |
| 1007 | refused | no |
| 1100 | wrong OTP | no |
| 1101 | OTP expired | no |
| 1102 | bad card data (number, non-existent card, expiry mismatch) | no |
| 1103 | card expired | no |
| 1104 | SMS notifications not enabled on the card | yes (after the holder enables them) |
| 1105 | duplicate | no |
| 1106 | OTP attempts exhausted | no |
| 1107 | card blocked | yes |
| 1108 | insufficient funds | yes, **with a new id** |
| 1109 | limit exceeded (SMS invoice sends per phone) | yes |
| 1110 | phone does not match the card's SMS-notification phone | yes |

"Retry" is the vendor's own column. For money-moving calls, first read the state back
(`getPayment`, `getHold`, `getInvoice`) before any retry.

## Webhooks

- Sent as `POST` to the `webhook_url` you passed (invoice, partial refund) when an operation
  finishes, successfully or not.
- Body: the invoice struct (checkout) or the payment struct (payments). See the product
  READMEs.
- Delivery is retried for about an hour until you answer **HTTP 200**. If it never succeeds,
  **the payment is cancelled and the money returned to the customer.** Answer 200 fast and
  process asynchronously.
- Verification: header `Signature` = `base64(HMAC-SHA256(key = <WEBHOOK_SECRET>, msg = raw
  request body bytes))`. Compute over the exact bytes received (before JSON parsing) and
  compare in constant time.

```python
import base64, hashlib, hmac

def valid(raw_body: bytes, signature_header: str, secret: bytes) -> bool:
    expected = base64.b64encode(hmac.new(secret, raw_body, hashlib.sha256).digest()).decode()
    return hmac.compare_digest(expected, signature_header or "")
```

## Sandbox

- Isolated replica on its own host (`https://api-dev.alifpay.uz/v2`), not connected to
  processing; no real money. It needs a sandbox `Token`.
- Test cards, the test OTP `111111`, the test PINFL, alif mobi QR test tokens, vendor samples
  and a minimum test plan: [`../sandbox/README.md`](../sandbox/README.md).
- A single charge or hold in the sandbox is capped at 5,000,000,000 tiyin; above that you get
  the insufficient-funds behaviour of the method used.
- Methods prefixed with `_` (`_payInvoiceWithMobi`, `_completeInstallmentRefund`) exist only
  in the test environment.

## Identifiers

- `id` of a payment, hold or refund is **client-generated** and unique per API client. Use a
  UUID and persist it before the call so you can read the state back after a timeout.
- Invoice `id` is generated by Alif and returned by `/invoice`.
- Vendor samples show truncated UUID-like ids; real ids are full strings.

## Changes in the current version (from the changelog, 2024-03-19)

- `/purchase` became `/pay`; `ref` became `id`; `charge` was removed and `amount` / `status`
  moved onto the payment struct; `receipt` changed from a boolean to an object holding
  `items` and `phone`; `payouts` added to `/pay` and `/invoice`.
- The invoice's `charge` attribute became `payment`; the invoice webhook body is now the
  invoice struct; the payment webhook body is the payment struct.
- Card summary: request id renamed `ref` -> `id`; range format `YYYY-MM-DD` -> `YYYY-MM`.
