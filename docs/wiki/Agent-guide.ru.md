# Гайд для агентов

[English](Agent-guide.md) · **Русский** · [Oʻzbekcha](Agent-guide.uz.md) · [简体中文](Agent-guide.zh-CN.md)

Эта страница для двух читателей: для людей, которые подключают скиллы к агенту, и для
агентов, которые читают репозиторий напрямую. Здесь объясняется, как устроены скиллы и как
выглядит хороший ответ.

## Устройство

Каждый скилл разделён на роутер и исполнителей: маленький роутер выбирает работу, а каждый
исполнитель получает только нужный ему контекст.

| Идея | Как её применяют скиллы |
|---|---|
| Маленький роутер выбирает исполнителя | `SKILL.md` — это роутер. Его description решает, когда скилл загрузится; в теле — таблица продуктов, таблица «какой продукт?», правила и предупреждения. Он не длиннее 180 строк. |
| Исполнитель получает только нужный контекст | В каждой папке продукта в `references/` лежат заметки, схемы и примеры. Агент открывает только ту папку, которая нужна задаче. |
| Быстрый путь в коде, медленный в модели | Подписи, заголовки авторизации, ссылки на оплату и форма payload идут через `sign.py` и `validate.py`. Модель читает и рассуждает только там, где код решить не может. |
| Inline и spill | То, что нужно в каждой задаче, лежит прямо в `SKILL.md`. Контракты, тестовые данные и чек-листы вынесены в файлы, которые читаются по необходимости. |
| Стабильные ID | Имена схем подписи (`click.prepare`), имена схем (`merchant/CreateTransaction`), ID предупреждений (`uzum.fiscal-receipt-24h`) и коды ошибок не меняются и не переводятся. |
| Ответ под канал | У чата, ревью PR и кода своя форма (ниже). |
| Evals держат в тонусе | Каждый кейс в `evals/` проверяет поведение, а не формулировку. См. [Evals](Evals.ru.md). |

## Как агенту работать с задачей

1. **Один провайдер за раз.** Для задачи про Payme и Click откройте `payme/SKILL.md`,
   закончите часть про Payme, потом откройте `click/SKILL.md`. Сравнивайте в конце. Правила
   единиц, авторизации и повторов не переносятся: Payme считает в tiyin, Click — в сумах.
2. **Выберите продукт по таблице решений**, потом откройте его
   `references/<product>/README.md`. Если в скилле есть `references/common/README.md`,
   прочитайте его первым: там транспорт, авторизация и конверт ошибок.
3. **Запустите инструменты**, прежде чем называть подпись, заголовок или payload
   правильными. Цитируйте их вывод.
4. **Проверьте жизненный цикл.** Если задача создаёт, подтверждает, отменяет, возвращает,
   повторяет или фискализирует что-либо, прочитайте блок скилла «Warn without being asked» и
   `references/lifecycle/README.md`. Назовите срок, можно ли откатить шаг и что будет с
   фискальным чеком, даже если никто не спрашивал. См. [Lifecycle](Lifecycle.ru.md).
5. **Берите тестовые данные из `references/sandbox/`** для тестов и примеров: тестовые
   хосты, карты, OTP-коды и сценарии ровно в том виде, в каком их публикует вендор. Никогда
   не придумывайте тестовую карту и прямо говорите, когда провайдер их не публикует (Paynet).
6. **Говорите, что не задокументировано.** Если в справках нет нужного факта, скажите, что
   документация его не описывает, и дайте ссылку на страницу из `Source:`. Не заполняйте
   пробел по памяти.
7. **Не называйте коммерческие условия.** Ставки комиссии, доли выплат и сроки расчётов
   зависят от договора каждого мерчанта. Поля комиссий в ответах API объяснять можно.

## Как выглядит хороший ответ

**В чате.** Сначала вывод, примерно в 100 словах, если пользователь не просил код. Точные
имена и коды — в обратных кавычках. По одной строке предупреждения на каждый подходящий
пункт жизненного цикла.

> Payme отклоняет её, потому что транзакции больше 12 ч. Отвечайте на `CreateTransaction`
> и `PerformTransaction` по ней ошибкой `-31008` и отмените её с `reason: 4`. Заказ не
> выполняйте. Повторы с тем же Payme `id` должны возвращать сохранённый ответ.
> Внимание: после проведения возврат — это полный `CancelTransaction` (state `-2`,
> reason `5`). Если Payme потом пришлёт `SetFiscalData` с `type: CANCEL`, сохраните его
> отдельным чеком и не трогайте чек `PERFORM`.

**В PR или ревью.** Problem, Change, Validation. Для ревью по чек-листу отмечайте каждый
пункт как pass, fail или n.a. со ссылкой `file:line`.

**В коде.** Работает как есть с песочницей, хранит секреты в переменных окружения, проверяет
подписи по сырому телу сравнением за постоянное время и хранит id транзакции провайдера как
ключ идемпотентности.

**На языке пользователя.** Русский, узбекский, китайский или английский, но имена методов,
поля, заголовки, коды и значения enum пишутся ровно так, как в API.

## Как спрашивать, чтобы получать хорошие ответы

- Называйте провайдера и продукт: «Uzum Merchant API», «Click SHOP API», «Payme Subscribe».
- Если что-то падает, вставьте сырое тело запроса и заголовки. Инструментам они нужны в
  том виде, в каком были отправлены.
- Скажите, куда пойдёт ответ: «для описания PR», «как обработчик на Go», «коротко, для чата».
- Для ревью попросите чек-лист: «проверь нашу интеграцию Multicard по чек-листу».
